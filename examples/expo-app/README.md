# Expo example app

A small project with a mobile app and a web app over one API, used to exercise the toolkit end to end: claimed ports, Metro, an API, a web dev server, a database per lane, a simulator or an emulator, launch with an API address, Maestro flows and Playwright tests. Its only account is a seeded test login, and it talks to no service beyond its own API.

|                            |                                                                                                            |
| -------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Bundle id                  | `com.example.expoapp` (also the Android package)                                                           |
| URL scheme                 | `expoexample`                                                                                              |
| Xcode workspace and scheme | `ios/ExpoExample.xcworkspace`, `ExpoExample` (generated by prebuild)                                       |
| Expo SDK                   | 57 (React Native 0.86), Expo Router, `expo-dev-client`                                                     |
| Package manager            | pnpm, with its own lockfile and `pnpm-workspace.yaml` (isolated installs, which Expo supports from SDK 54) |
| Web app                    | Vite 8 with React 19, in `web/`                                                                            |
| Database                   | SQLite through Node's built-in `node:sqlite`, one file per lane                                            |
| Test account               | `tester@example.com`, password `example-password` (seeded by the first migration)                          |

## What's in it

- **Home** (`src/app/index.tsx`): a counter button, a text input, a switch, a ticker that changes every second, buttons to the sheet, Details and API, and a list of 40 rows, most of them off screen.
- **Sheet** (`src/app/sheet.tsx`): a native form sheet at 40% height, closed by its button or by dragging it down.
- **Details** (`src/app/details.tsx`): a second screen on the stack.
- **API** (`src/app/api.tsx`): calls `GET /items` on the API and shows the result, an error state when the API can't be reached, and a "No API configured" state when the app was launched without an API address.
- **Web app** (`web/`): a sign-in page, then a signed-in page that lists the places from `GET /items`, says which API port served them, orders them shortest first on request, and adds a place through `POST /items`. The Vite dev server proxies `/api/*` to the API named by `API_URL`, so the session cookie belongs to the web app's own origin.
- **API server** (`api/server.mjs`): dependency-free Node. It listens on `127.0.0.1:$PORT` (no default port; `0` picks a free one) and logs one line per request to stdout. It opens the SQLite file at `$DATABASE_PATH` and applies any migration it lacks.
- **Database** (`api/database.mjs`): the schema, the migrations (users, sessions and places, then the seeded test account and three places) and `node api/database.mjs create [path]`, which creates and migrates a database. Without a path it uses `$TMPDIR/expo-example-databases/$AGENTLANE_LANE.sqlite`, and when `$AGENTLANE_EXPORTS` is set it writes `DATABASE_PATH=<path>` there.

The mobile app reads its API address from the `-apiBaseUrl` launch argument on iOS (React Native's iOS `Settings` reads the launch-argument domain) and from the `apiBaseUrl` string extra of the intent that opened it on Android (the local Expo module in `modules/launch-arguments`), never from a baked-in default.

### The API

| Request           | Signed in | Answer                                                                                            |
| ----------------- | --------- | ------------------------------------------------------------------------------------------------- |
| `GET /health`     | no        | `{"status":"ok"}`                                                                                 |
| `GET /items`      | no        | `{"items":[{"id","name","minutes"}],"port"}`, the places in the order they were added             |
| `POST /items`     | yes       | `{"name","minutes"}` (1 to 80 characters, 1 to 600 minutes) adds a place: 201 `{"item"}`          |
| `POST /session`   | no        | `{"email","password"}` signs in: `{"user","token"}` and a `session` cookie; 401 for a wrong login |
| `GET /session`    | yes       | `{"user"}`, or 401                                                                                |
| `DELETE /session` | no        | signs out and clears the cookie: 204                                                              |

A request is signed in by the `session` cookie (the web app) or by `Authorization: Bearer <token>` with the token `POST /session` returned (any other client). The mobile app reads `GET /items` and doesn't sign in.

### A database per lane

`agentlane.json` declares the database as the resource `db`. When `up` first runs for a lane, the toolkit runs `node api/database.mjs create`, which creates the lane's file and exports `DATABASE_PATH`. The API, `exec` and the hooks get that value, so two lanes never share a row. When the lane is released, or reaped after its session died, the toolkit runs the teardown, `rm -f -- "${DATABASE_PATH:?}" "$DATABASE_PATH-journal"`, which needs no file from the worktree. A database lives as long as its lane: a second `up` keeps it, and `release` then `up` starts from the seed again.

### Signing in the lane's browser

On `up --platform web` the toolkit opens the web app in the lane's own browser, then runs the `signin` hook, `node scripts/signin.mjs`. It signs the test account in through `POST /api/session` on the web app's origin and writes the `session` cookie to `$AGENTLANE_STORAGE_STATE` in Playwright's storage-state format; the toolkit loads that into the browser, which then shows the signed-in page. On iOS and Android the hook does nothing. Metro runs only for the mobile platforms (`"platforms": ["ios", "android"]`).

## Commands

Ports below are examples; use the ports you claimed. Never serve Metro on 8081 or 8082.

```bash
cd examples/expo-app

# setup
pnpm install --frozen-lockfile

# build: prebuild (ios/ is generated, not committed), pod install, xcodebuild, install on the simulator
scripts/build-ios.sh <simulator-udid>

# services
node api/database.mjs create /tmp/expo-example.sqlite         # creates and migrates a database at that path
PORT=41218 DATABASE_PATH=/tmp/expo-example.sqlite node api/server.mjs  # ready when GET http://127.0.0.1:41218/health returns 200
API_URL=http://127.0.0.1:41218 node_modules/.bin/vite web --port 41318 --strictPort --host 127.0.0.1  # the web app at http://localhost:41318/
node_modules/.bin/expo start --dev-client --port 41118 </dev/null  # ready when GET http://localhost:41118/status returns packager-status:running

# launch: pre-approves the scheme, launches with -apiBaseUrl, then opens the dev-client link to Metro
scripts/launch-ios.sh <simulator-udid> 41118 41218
```

Leave out the API port to launch with no API configured: `scripts/launch-ios.sh <simulator-udid> 41118`.

`launch-ios.sh` does three things a launch helper needs:

1. Writes `com.apple.CoreSimulator.CoreSimulatorBridge-->expoexample` into the simulator's `com.apple.launchservices.schemeapproval.plist`, so `simctl openurl` doesn't stop at "Open in Expo Example?". iOS reads that file at boot, so a new approval on a running simulator costs a reboot; `build-ios.sh` writes it before the first boot.
2. `xcrun simctl launch <udid> com.example.expoapp -apiBaseUrl http://localhost:<api-port>`.
3. `xcrun simctl openurl <udid> 'expoexample://expo-development-client/?url=http%3A%2F%2Flocalhost%3A<metro-port>'`, which the running dev client opens in place, keeping its launch arguments.

The dev client is configured with `launchMode: "launcher"`, so a plain launch never reopens the last Metro URL (which could be another worktree's). The dev menu's onboarding screen, launch-time menu and floating button are turned off in `Info.plist` through `app.json`, so they never cover the app in a flow.

## Android

`agentlane up --platform android` does all of this on an emulator from the toolkit's pool. By hand, with an emulator serial such as `emulator-5584`:

```bash
scripts/build-android.sh                       # expo prebuild for Android, Gradle with JDK 17, writes build/android/app-debug.apk
adb -s emulator-5584 install -r build/android/app-debug.apk
adb -s emulator-5584 reverse tcp:41118 tcp:41118   # the emulator's localhost:41118 is this Mac's Metro
adb -s emulator-5584 reverse tcp:41218 tcp:41218   # and its API
adb -s emulator-5584 shell "am start -a android.intent.action.VIEW -d 'expoexample://expo-development-client/?url=http%3A%2F%2Flocalhost%3A41118' --es apiBaseUrl http://localhost:41218 com.example.expoapp"
```

`adb reverse` keeps the addresses the same as on a simulator, so the app dials `http://localhost:<port>` on both. The dev menu's onboarding, launch-time menu and floating button are turned off through application meta-data written by `plugins/with-android-dev-menu.js`.

## Maestro flows

Each flow launches the app itself, so flows run in any order and from a fresh state. They need the app installed and Metro (and, for most, the API) running, and take the ports as parameters:

```bash
maestro --device <udid> test -e METRO_PORT=41118 -e API_PORT=41218 .maestro
```

`launchApp` passes its `arguments` to `simctl launch` (a key without a leading `-` gets one), so a flow launches with `--initialUrl http://localhost:<metro-port> -apiBaseUrl http://localhost:<api-port>`. The dev client loads `--initialUrl` straight away, with no deep link and so no "Open in" prompt.

On Android `launchApp` passes its `arguments` as intent extras, and the dev client takes its bundler only from a link. Each flow therefore waits for the dev launcher's screen and then opens the dev-client link (a link that arrives before that screen is up loads nothing). The emulator needs the `adb reverse` rules above. Run them with `maestro --device <serial> test ...`.

The two launch-state flows in `.maestro/states/` aren't part of the suite:

```bash
maestro --device <udid> test -e METRO_PORT=41118 .maestro/states/no-api.yaml
# with the API stopped:
maestro --device <udid> test -e METRO_PORT=41118 -e API_PORT=41218 .maestro/states/api-down.yaml
```

## Web tests

`playwright.config.ts` runs the Playwright tests in `web/tests/`, with `@playwright/test` pinned to the toolkit's Playwright (1.64.0):

- `signed-out.spec.ts` starts signed out: a wrong password is refused, signing in through the form shows the places, and signing out makes the API refuse writes.
- `signed-in.spec.ts` starts from a saved login: the seeded places, a place added on the page that is still there after a reload and in `GET /items`, and Shortest first.

```bash
agentlane exec -- npx playwright test    # against the lane's web app, in the toolkit's pinned Chromium, from the lane's saved login
pnpm exec playwright install chromium    # without the toolkit, once: the browser Playwright drives
pnpm run test:web                        # without the toolkit: starts its own API (database in memory) and web server on free ports
```

Under `agentlane exec`, the tests start no server and use `$AGENTLANE_WEB_URL`. The signed-in ones start from `$AGENTLANE_STORAGE_STATE`, the login the `signin` hook saved, and a place they add stays in the lane's database. Each run writes its output to `$AGENTLANE_EVIDENCE/<stamp>-playwright-test/`, with a `trace.zip` per failed test (`npx playwright show-trace <file>`), and the folder outlives `release`. Without the toolkit, a `sign-in` setup project signs in through the form and saves the login to `web/.auth/tester.json`, and the output goes to `web/test-results/`.

## The toolkit and its Claude Code plugin

The example depends on the toolkit in this repository (`"agentlane": "link:../.."`), so `node_modules/.bin/agentlane` runs this checkout's build. Build the toolkit once before you use it here:

```bash
(cd ../.. && pnpm install --frozen-lockfile && pnpm run build)
pnpm install --frozen-lockfile
node_modules/.bin/agentlane up                  # the iOS app, with Metro, the API and the web app
node_modules/.bin/agentlane up --platform web   # the web app in the lane's own browser, signed in: no simulator or Metro, ready in seconds
```

`.claude/settings.json` declares this repository's marketplace (`.claude-plugin/marketplace.json` at the root; a relative `directory` path resolves against the repository's main checkout) and enables its plugin, `agentlane@agentlane`. The plugin brings the `look`, `run` and `screenshot` tools, served by `node_modules/.bin/agentlane mcp`.

Claude Code applies a project's `extraKnownMarketplaces` only in a folder you trusted. Open `claude` in `examples/expo-app` once and accept the trust dialog. A headless `claude -p` run never accepts it, so until you have, the marketplace is ignored there without a message (see "Require plugins per repository" in https://code.claude.com/docs/en/plugins/org). For a one-off headless run without trusting the folder, pass the marketplace with `--settings`:

```bash
printf '{"extraKnownMarketplaces":{"agentlane":{"source":{"source":"directory","path":"%s"}}}}' "$(git rev-parse --show-toplevel)" > /tmp/agentlane-marketplace.json
CLAUDE_CODE_SYNC_PLUGIN_INSTALL=1 claude -p --settings /tmp/agentlane-marketplace.json '...'
```
