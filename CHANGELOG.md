# Changelog

Newest first.

## Unreleased

A lane now gives its simulator or emulator back when nobody uses it, and ends on its own once its session is gone, whether or not the session ran `release` or its session-end hook fired. The hooks move into every agent's project settings, plugin or not, and `doctor` proves they run. `prune` and the tool installs leave less on disk. This version runs beside 0.4.1 on the same Mac; "Sharing a Mac with 0.4.1" lists what 0.4.1 still does differently.

### Moving from 0.4.1

1. **Run `init` again in each project, and commit what it changes.** `node_modules/.bin/agentlane init`, with the agents the project uses, rewrites the guard and session-end hooks in each agent's project settings. The new hooks start the toolkit only for commands that name a device or browser tool, find the toolkit in another worktree of the repository, and read names split by quotes, backslashes, line continuations, `$"…"` or brace expansion. Until then, `doctor` warns that the hooks are stale. Codex asks you to trust the changed hooks again with `/hooks`. The Claude Code plugin's own hooks update with the plugin.
2. **Projects that leave Claude Code's hooks to the plugin need that run too.** A project whose `.claude/settings.json` enables `agentlane@agentlane` or `agent-env@agent-env` and has no hooks of its own gets them from `init`, which renames the 0.2.x plugin key as before. Until then, `doctor` fails `hooks claude` on a Mac where the plugin isn't installed, because no hook runs there.
3. **Hold the lanes a person looks at.** A lane now parks 30 minutes after its last call, so a simulator left up for someone to look at shuts down. The `dev-loop` and `drive` skills tell agents to run `agentlane keep`, and a script that leaves an app up for a person runs it too.
4. **Leave `config.json`'s `idleHours` until 0.4.1 is gone.** This version accepts it and ignores it, because no lane takes over another any more. Remove it once no project on the Mac runs 0.4.1 or earlier. Don't set `parkMinutes` while one does: those versions refuse a `config.json` with a setting they don't know.
5. **Update scripts that read the JSON.** `claim --json` drops `tookOver` and `freed`. `prune --json` drops `unrecorded`: read `orphans`, and `kept` for the devices kept with a reason. `lanes --json` and `status --json` add `park`, `hold` and `ownerGone` to each lane, and `state` (`running`, `gone` or `unknown`) and `aliveAt` to its processes.
6. **Run `prune` with your state variables.** If a project or shell sets `AGENTLANE_STATE_DIR` or `AGENT_ENV_STATE_DIR`, run `prune` with the same variables that project's agentlane runs with. `prune --yes` now deletes a shut-down device named like a pool device that no registry it reads records, so a device whose lane is in a registry it doesn't read is deleted.
7. **To get 0.2.x's disk back, release its lanes first.** `prune --yes` deletes 0.2.x's downloads and build cache only while no registry 0.2.x may use has a lane or a waiting claim. Where agentlane shares 0.2.x's state folder, that counts every lane, so release them all (`agentlane status` lists none), then run `prune --yes` from each project that ran 0.2.x, so its build cache is covered.
8. **Delete old init backups by hand.** `init` now keeps its five newest backups per project. It never removes the ones earlier versions named without the project hash (`<state dir>/init-backups/<stamp>-<folder>`).

### Sharing a Mac with 0.4.1

- **One registry, still format 1.** This version adds tables 0.4.1 doesn't read (`parks`, `holds`, `owner_checks`, `device_leases`, `process_alive`) and keeps the format version 0.4.1 checks. When 0.4.1 ends a lane, its park, hold and checks go with it.
- **A parked lane is a live lane to 0.4.1.** 0.4.1 sees it alive, with its ports held, and sees its device as free.
- **0.4.1 still ends a gone owner's lane at once.** Its own claims end such a lane as soon as they find it, and judge a Claude Code owner by its pid. So the 30-minute window in which a returning session takes its lane back holds once every project on the Mac has upgraded.
- **0.4.1 can still take over a parked or held lane.** Once a lane's last call is over 2 hours old (its `idleHours`), a 0.4.1 claim short of ports or devices can take the lane and end it, teardowns included. Nothing is handed to two lanes, but a lane of this version can end that way. A `keep` counts as a call, so it puts that off.
- **0.4.1 refuses a `config.json` that sets `parkMinutes`**, with "unknown setting 'parkMinutes'".
- **A device shutdown cut short.** If a process of this version is killed while it shuts a device down, and only 0.4.1 processes run afterwards, that device's slot and memory stay held until a process of this version claims or releases, or the Mac restarts. Meanwhile, 0.4.1 claims that need the slot are refused `pool-busy`, naming "a process claiming a lane (pid 1)". No second device is made.
- **A pool over its size.** If a Mac restart with 0.4.1 in use leaves the pool with more devices than its size, this version deletes the extra device once its shutdown or delete ends, with a note. If that delete fails, the device stays until `agentlane prune`.
- **Tool versions.** A lane of 0.4.1 runs agent-browser without naming its browser, so while one does, every older browser stays. A project still on 0.4.1 downloads its tools again the next time it needs them, if nothing used them when they were removed.

### New

- **Parking.** While its owner is alive, a lane parks 30 minutes after its last call. Its dev servers, browser, driver and Maestro stop, its recordings end, its simulator or emulator shuts down and goes back to the pool, and its bundler pin, dial defaults and `adb reverse` rules are removed. It keeps its ports, its resources, its browser's saved login and its record. The next call brings it all back before it runs: `exec`, `restart`, `up`, any MCP tool, and the CLI's `look`, `run`, `screenshot`, `record`, `driver start`, `evidence` and `device`. With the pool full, that call waits for a device as `up` does. A call that comes while the lane is being parked or brought back waits up to 30 minutes, then is refused with the new code `lane-busy`. `status` shows `parked since …; its next call brings back …`, `lanes --json` has a `park` field, and `doctor` warns `parked`. The window is `parkMinutes` in `config.json`, 30 by default.
- **`agentlane keep --for <time> --reason <text>`** holds this session's lane for its folder up past the park window, while a person looks at the running app. `--for` takes minutes or hours (`45m`, `2h`, `1h30m`), 1 hour when left out and 24 hours at most; a longer or malformed time is refused with exit 2. `--reason` is required. A second `keep` replaces the first. `keep` counts as a call, and on a parked lane it doesn't wake anything: the next call brings the lane back and the hold keeps it up. `release` ends the hold with the lane, and so does the owner being found gone. `status` shows `held until <time> (<left> left): <reason>`, and `lanes --json` has a `hold` field. No setting holds lanes by default.
- **A lane whose owner is gone ends on its own.** An owner is gone when its process has exited, its pid belongs to another process, or the lane's folder was deleted. The sweep finds such a lane within 5 minutes while any agentlane MCP server runs, and otherwise at the next agentlane command. It parks the lane at once, and 30 minutes later ends it with everything `release` does. In that window, the owner's Claude Code session (by `CLAUDE_CODE_SESSION_ID`) or Codex thread takes the lane back, with its ports and resources, by calling on it from its folder; the next call wakes it. No other session gets the lane. `status` shows an `owner gone` line with when the lane ends and which session can take it back, and `lanes --json` has `ownerGone`. A session-end hook still releases at once.
- **The sweep.** There is no daemon. Every agentlane command checks, from one registry read, whether the sweep has work, and when it does starts it in a detached process and carries on. Each running MCP server does the same every minute. The sweep parks lanes past the window, checks the owners no call has shown alive in the last few minutes, ends lanes whose window has passed, stops a screen recording an ended lane left running (only after `ps` proves the pid is that recorder), and removes an ended lane's folder, evidence included, seven days after the lane ended. It logs to `sweep.log` in the state folder.
- **`agentlane reap [--json]`** runs the sweep now and prints what it did, for running from cron or launchd.
- **The guard counts as a call.** A `simctl`, `adb`, `playwright-cli` or `agent-browser` command the guard lets through on the session's own device or browser counts as a call on that lane, so a lane an agent drives by hand isn't parked.
- **`doctor` proves the hooks run.** A `hooks <agent>` line per wired agent reads the mark the hook left the last time it reached the toolkit. When the mark is missing, over a day old, from another toolkit or older than the hook file, the toolkit's files or the Node the hook ran on, doctor runs the guard hook on a harmless command. The line fails with a fix when the hook can't run: no toolkit, a dangling `node_modules/.bin/agentlane`, a broken command, a missing hook script, or a Claude Code plugin that the project leaves the hooks to and that isn't installed. When the toolkit is older than doctor, it says to update it. `doctor` also warns when the project enables the plugin and Claude Code hasn't installed it.
- **`status` checks the processes it lists.** Each process a lane started shows as running, gone or can't tell. A pid another process has taken counts as gone.
- **`prune` finds lost devices and what 0.2.x left.** It lists the simulators and emulators named like pool devices (`agentlane-pool-*`, `agentlane-emu-*`, `agent-env-pool-*`, `agent-env-emu-*`) that no registry it reads records, each with its size, and `prune --yes` deletes them, only while simctl or adb lists them as shut down. It reads the registries in `$AGENTLANE_STATE_DIR` and `$AGENT_ENV_STATE_DIR` when set, and in the `agentlane` and `agent-env` folders of `$XDG_STATE_HOME` and `~/.local/state`. Before each deletion it locks them all and checks again. This reverses 0.3.0's promise that a device the registry has no record of is never deleted; 0.3.0 kept them because a registry in another state folder might hold them, which is still true of a folder none of those variables names. prune also lists 0.2.x's downloads in `~/.local/share/agent-env` and its build cache in `.git/agent-env`, in this repository and every repository a registry names, and deletes them only while no registry 0.2.x may use has a lane or a waiting claim. It refuses a folder whose real path isn't 0.2.x's own. Before deleting one it renames it to `<path>.removing-<time>-<hex>`, so a second prune can't give it back to a 0.2.x lane; if a 0.2.x lane appears while prune works, prune puts back what it moved, and the next `prune --yes` finishes or undoes a run that stopped partway.
- **Older tool versions go.** Once agentlane has installed and checked a newer pin of its patched Maestro, playwright-core, Chrome for Testing, the headless shell, ffmpeg or agent-browser, it removes the older versions it installed itself in `~/.local/share/agentlane`. A version stays while a running process names it, a lane's files in this version's registry or 0.2.x's name it, another process is installing it, a kept version runs it, or, for a browser, a link in the browsers folder's `.links` names it, such as the one a project's own `npx playwright install` writes. If `ps` or a registry can't be read, nothing is removed. It never removes newer versions, folders without its install marker, or `~/.local/share/agent-env`. agent-browser lanes now name their browsers in `bin/.browsers`, and the lane's `agent-browser` sets `AGENT_BROWSER_EXECUTABLE_PATH` to its headless shell. A Maestro from an earlier pin, such as `2.11.0-agentenv.3`, goes at the first install of the current one unless something uses it.
- **agentlane's own files have limits.** A lane's recorded steps (`<state>/driver/<id>.steps.jsonl`) keep the newest 512 KiB of runs once they pass 1 MiB, so in a very long session the oldest steps drop out of `record save`. Each run records when it ran, and a device trace that spans a cut holds only the runs after `evidence trace start`. `<state>/emulators/<avd>.log` moves to `<name>.1` when it passes 5 MiB at a boot, and `session-end.log` and `sweep.log` when they pass 1 MiB. `init` names its backups `<stamp>-<folder>-<hash of the project's path>` and keeps the five newest per project. Evidence folders are never cut.
- **A Postgres recipe.** The resources page shows how to clone each lane's database from a template built once per migrations fingerprint, with `examples/expo-app/scripts/lane-pg.sh`.

### Changed

- **No lane takes over another.** At any idle age, a claim short of a device waits in the queue, and a claim short of ports is refused, naming the lanes that hold them.
- **A claim no longer ends other sessions' lanes.** It records a gone owner and leaves the lane to the sweep.
- **The hooks always go in each agent's project settings.** `init` writes Claude Code's guard and session-end hooks into `.claude/settings.json` even when the project enables the plugin, which still brings the skills and the MCP server. There the session-end hook gets its declared 10 seconds; Claude Code gives a plugin's session-end hook 1.5 seconds whatever it declares, so the plugin's hook only starts the release. Where both copies run, both guards answer the same and one release runs. The hooks look for the toolkit from the hook's folder upwards, then in the repository's other worktrees.
- **The hooks start Node only for device and browser commands.** The hooks `init` writes check in the shell that the command names `simctl`, `adb`, `emulator`, `avdmanager`, `playwright-cli`, `@playwright/cli` or `agent-browser` before they start the toolkit, as the plugin's hook already did. Both read names split by quotes, backslashes, line continuations (in Copilot's hook input too), `$"…"` or brace expansion, and a command with braces that names none of them, such as `mkdir -p src/{a,b}`, starts no Node.
- **The guard reads `$"…"` quoting and brace expansion.** It judges `a$"db" shell`, `a{d,}b shell`, `e{nv,mulator} -avd …` and `adb -s emulator-55{54,60} …` as the commands bash runs.
- **Every call on a lane counts as its last use.** `driver stop`, `doctor`, `keep` and `touch` count, and so do evidence commands and device controls that fail. `driver status` and `evidence list` don't. A long `exec` command, `up` hook or tool call counts once a minute while it runs. When the registry is busy, a driving command records its use in the lane's folder (`last-call.json`) and carries on, instead of waiting up to 120 seconds and failing.
- **Slow device work runs outside the registry's lock.** A claim, an `up`, a release and the driver's last-used updates no longer wait while another lane creates a simulator or AVD, lists devices or shuts one down. While a pool device is being shut down or deleted, `status` lists it as `<device name>.shutdown.<hex>` (or `.delete.`) in state `creating`, a `pool-busy` refusal names "a process shutting down <device> (pid N)", and `prune` keeps it with that pid. Where `ps` can't read pid 1, as in some sandboxes, shutdowns and deletes still run inside the lock. A claim that keeps seeing lanes end while it lists devices looks again while its `--timeout` lasts, then is refused `pool-busy`, naming the lanes that ended.
- **An interrupted release finishes later.** If a release is stopped while it shuts its device down, the next claim or release finishes the shutdown and puts the device back in the pool shut down, where a recovering release used to put it back booted.
- **Stopping a service whose leader has exited.** `release`, `restart`, a park and a reap stop the processes a service started that outlive its leader, where they used to refuse with a `kill` hint. They stop the processes left in the service's group that started with its leader or before agentlane last saw the leader running, which covers the workers of an `exec`-style dev server (expo, vite, a node API) whose main process died first. agentlane records that sighting when the service passes its ready check, and the sweep records it again at most every 10 minutes. Without that proof they still refuse, with the hint. After the grace, SIGKILL goes to the whole group, so helpers started after SIGTERM end too. If `ps` can't list the processes a service started outside its group, they ask once more and then stop the group anyway, reporting those processes as not found, or as left alone with a `kill` command.
- **Stop messages say who got what.** `stopped api (…) with SIGKILL to process group 4242, which SIGTERM did not end` replaces `… with SIGKILL after SIGTERM was ignored`, and a stop that can't prove what is left says what it sent. When a process can't be checked, `release`, `restart`, `doctor` and `up` name the read that failed (`ps could not read when it started`, `its working directory could not be read`) instead of "ps or lsof failed".
- **`up` asks each question once.** It runs `xcrun simctl list runtimes`, `xcodebuild -version` and the Java 17 search once per `up` and hands the driver the JDK it found, reads the simulator's state once before booting and once after, no longer lists devices just to prune lane files, and reuses each cache input's hash after the build.
- **Ended lanes' folders go seven days after the lane ended.** `up`, `claim` and the sweep count from the end the registry records, where they used to count from the folder's last write, which could remove a week-old lane's evidence as soon as it ended.
- **`prune` needs `HOME`**, and exits 2 without it.

### Fixed

- A browser lane driven only through the MCP tools counts as in use. Its last use never moved, so another lane could take it over while it was in use.
- A reap does everything a release does. 0.4.1's reap of a dead owner's lane skipped its recordings, the bundler pin, the dial defaults, the `adb reverse` rules and the project's teardown hook.
- A service that fails to start and can't be stopped afterwards stays in the lane's record, and the failure says so. The lane used to forget a process that may still have been running.
- A dev server that has exited but whose parent hasn't collected it yet is reported stopped, not as having survived SIGKILL.
- An invalid `config.json` no longer shuts down a lane's warm driver. The driver, and a long command's once-a-minute count, try the last-used update again until the file reads.
- A claim no longer refuses a free port as "held by processes the registry did not start" when the process probing it was busy for over half a second.
- `up`'s preflight, the driver and `maestro/build.sh` ask `java_home` for JDK 17 with `-F`, so a Mac with JDK 21 registered and an unregistered JDK 17, such as Homebrew's `openjdk@17`, finds Homebrew's.
- The driver looks past a `JAVA_HOME` that names a JDK other than 17 for one that is, as `up` does, so a driver `up` started restarts after an idle stop or a crash. A non-17 `AGENTLANE_JAVA_HOME` is still refused.
- `prune` shuts down a free pool simulator that simctl lists as booting or shutting down before it deletes it, and lists it as "starting or stopping, so it is shut down first" (`"state": "changing"` in `--json`).
- `prune --yes` reports what happened when its registry lock fails to commit after a step: a 0.2.x folder it took for removal is deleted and reported deleted, and one it put back for a 0.2.x lane is reported put back.
- On Linux, a reap or release stops the services of a lane whose worktree folder was deleted. It used to leave them running, with `pid N is no longer in <folder>`, because Linux names a deleted working folder with ` (deleted)` after it.

## 0.4.0

### New

- **`npx agentlane init` with no flags.** init wires the agents whose files the project has (`CLAUDE.md`, `.codex/`, `.cursor/`, `.github/copilot-instructions.md`, `GEMINI.md`, `.agents/rules/` and others) or whose session runs it, and prints the reason for each. In a terminal it lists all six agents, checks the ones it found, and takes Enter, numbers or names. With no terminal and nothing found, it exits 2 and names `--agents` and `--all`, which work as before.
- **init installs the toolkit.** When the project's `package.json` doesn't list `agentlane`, init adds it as a dev dependency at its own version with the project's package manager (from the `packageManager` field or the lockfile: pnpm, yarn, bun or npm). A project with no `package.json` gets a private one. When the install fails, init keeps the files it wrote, exits 1 and prints the command to run. A project that already lists another version keeps it, and init says so. `--check` installs nothing.

### Fixed

- Maestro starts with the JDK in `AGENTLANE_JAVA_HOME` when `JAVA_HOME` is another version. `up`, `doctor` and the Android build already read it first, but `look`, `screenshot` and the other driving commands read only `JAVA_HOME`, so they refused a Java 21 `JAVA_HOME` that `doctor` had passed.
- `up` and `doctor` no longer fail capture hygiene on a Mac where the simulator reads its pinned status-bar time back as `9:41`. They accepted only `09:41`, which is how some Macs print it.
- `init` no longer lists 0.2.x's `.github/hooks/agent-env.json` as `unchanged` in a project that doesn't have it. It lists that file only when it changes or removes it.
- Under `exec` and in the signin hook, `maestro` is the lane's own Maestro, or it prints why the lane has none and exits 2. A lane whose `agentlane.json` was invalid or had no `driver` block, or that held no running simulator or emulator, ran whatever `maestro` came first on PATH, unbound to the lane's device, after one warning that named only the file. The message now gives the config's problems, or what is missing and how to add it. A project that ran its own Maestro under `exec` without a `driver` block adds `"driver": {}` to `agentlane.json`.
- The lane's `maestro` refuses `maestro mcp`, which takes its device from each tool call, so the lane can't bind it to its device. The lane's MCP server is `node_modules/.bin/agentlane mcp`.
- `maestro test`'s output goes to the lane's evidence folder only when `test` is the subcommand. A flow file named `test`, given to another subcommand, got a `--debug-output` folder too.
- On macOS, `agentlane driver install --from <zip>` clears the `com.apple.quarantine` attribute from the Maestro it unpacks. macOS's `unzip` copied a browser-downloaded zip's quarantine onto every unpacked file. Install still checks the zip's sha256 before unpacking.

### The patched Maestro

The patched Maestro build is renamed `2.11.0-agentlane.1`, and the toolkit downloads it over https from this repository's release, so first use no longer needs a signed-in `gh`. Compared with `2.11.0-agentenv.3`:

- The MCP `run` tool's result lists only the `env` the call passed. It used to list every `MAESTRO_*` variable in the driver's own environment as well. Flows still get those variables.
- On Android, a `tapOn` with `retryTapIfNoChange: true` and `waitToSettleTimeoutMs: 0` taps a second time again when the first tap changed nothing. The quick tap, which sends `retryTapIfNoChange: false`, still reads no hierarchy after the tap.
- When an iOS runner never answers within the startup timeout, Maestro stops the `xcodebuild` it launched for it. Before, `maestro test` left that `xcodebuild` running after it exited.
- On iOS, `maestro record`, `maestro hierarchy` and `maestro query` take a runner port the OS assigns when you pass no `--driver-host-port`, as `maestro test` already did. They used the fixed port 22087, so two lanes running them at once collided, and the second failed with "The XCTest runner port 127.0.0.1:22087 is held by a Maestro runner that refuses this process's token". A `--driver-host-port` you pass still wins.

## 0.3.0

The toolkit is called agentlane now, and what each agent session holds is a lane. The package, the command, the config file, the environment variables, the plugin, the output and the JSON all say agentlane and lane. Besides the rename, 0.3.0 adds `prune`, browsers for Intel Macs and Linux, and the fixes listed under New and Fixed. You still claim and release a lane, so the `claim` and `release` commands keep their names. 0.3.0 runs beside 0.2.x on the same Mac, so projects can move one at a time.

### Moving from 0.2.x

1. **Release the project's lanes first.** In each worktree, while 0.2.x is still installed, run `node_modules/.bin/agent-env release`. A lane 0.2.x started keeps 0.2.x's variables in its services and driver.
2. **Replace the dependency.** The package is `agentlane`, at 0.3.0, and its bin is `node_modules/.bin/agentlane`.
3. **Rename the config.** `agent-env.json` becomes `agentlane.json`, and its `"$schema"` points at `agentlane.schema.json`. `up`, `doctor` and `restart` refuse a project that still has only `agent-env.json`, and their message names these renames.
4. **Rename the variables.** Every `AGENT_ENV_` variable is `AGENTLANE_` now, in the config's commands, hooks, scripts, Maestro flows and test configs. Two change more than the prefix: `AGENT_ENV_CLAIM` is `AGENTLANE_LANE`, and `AGENT_ENV_CLAIM_TOKEN` is `AGENTLANE_LANE_TOKEN`. The settings you set yourself follow the prefix: `AGENTLANE_STATE_DIR`, `AGENTLANE_OWNER_PID`, `AGENTLANE_JAVA_HOME`, `AGENTLANE_MAESTRO` and `AGENTLANE_PLAYWRIGHT_BROWSERS`.
5. **Run `init` once.** `node_modules/.bin/agentlane init --agents <list>` replaces what 0.2.x's `init` wrote instead of adding a second copy. MCP server entries named `agent-env` become `agentlane`, and `.codex/config.toml` loses `[mcp_servers.agent-env]`. Hooks that ran `node_modules/.bin/agent-env` run `node_modules/.bin/agentlane`, and `.github/hooks/agent-env.json` becomes `.github/hooks/agentlane.json`. The skill stubs run `agentlane skills get`, and `disabledMcpjsonServers` names `agentlane`. Until `init` has run, `doctor` warns that the wiring is stale.
6. **The Claude Code plugin is `agentlane@agentlane`.** Where `.claude/settings.json` enables `agent-env@agent-env`, `init` enables `agentlane@agentlane` instead and renames the marketplace entry `agent-env` to `agentlane`, keeping its source. Rename an `agent-env@…` entry in your local or user settings by hand. The setup skill is `/agentlane:setup`, and the MCP server is `plugin:agentlane:device`. The marketplace's repository is still `north-star-hq/agent-env`.
7. **Update scripts that read the CLI.** The renamed commands, flags and JSON fields are listed below.
8. **Expect one uncached build.** The build cache moves to `.git/agentlane/build-cache`. The pinned Maestro, Playwright and agent-browser download again into `~/.local/share/agentlane/`. Once no worktree of the project runs 0.2.x, you can delete `.git/agent-env/`, and once nothing on the Mac runs it, `~/.local/share/agent-env/`.

### Renamed

- `claims --json` is `lanes --json`. Its output is `version: 2`: `claims` is `lanes`, a pool device's `claimId` is `laneId`, and a pending teardown's `claim` is `lane`.
- `release --claim <id>` is `release --lane <id>`.
- In `claim --json` and `up --json`, `claim` is `lane`. In `release --json`, each teardown's `claim` is `lane`. `driver status --json` gives `laneId`. `doctor`'s `claim` check is the `lane` check, and the refusal `claim-gone` is `lane-gone`.
- The CLI's output, the MCP tools' descriptions, the schema and the skills say lane. `claim` prints `claimed lane <id>`, and `status` lists `lanes`.
- Each lane's folder is `<state dir>/lanes/<id>`, where `$AGENTLANE_LOGS` and `$AGENTLANE_EVIDENCE` point.
- New pool devices are `agentlane-pool-*` simulators and `agentlane-emu-*` emulators.
- The bench report's schema is `agentlane-bench/1`.

### Sharing a Mac with 0.2.x

- **One registry.** While `~/.local/state/agent-env/registry.sqlite` exists and `~/.local/state/agentlane/registry.sqlite` doesn't, 0.3.0 uses 0.2.x's state folder as it is. Both versions then see every lane, and neither hands out a port, simulator, emulator or browser profile the other holds. A Mac that never ran 0.2.x gets `~/.local/state/agentlane/`.
- **0.2.x's names in 0.2.x's folder.** There, 0.3.0 writes only what 0.2.x reads: the registry stays format 1, lane folders stay under `claims/`, and new pool devices are named `agent-env-pool-*` and `agent-env-emu-*`, because 0.2.x boots only emulators with its own prefix. So either version can reap the other's lane once its owner is gone: stop its services, driver and browser, and run its resources' teardowns.
- **0.2.x's pool devices stay in the pool.** A free one goes to the next lane of either version, and 0.3.0 boots, stops and deletes `agent-env-emu-*` emulators as its own. `agentlane prune --yes` deletes the free ones along with 0.3.0's, and never one a 0.2.x lane holds.
- **Moving the folder.** Once no project on the Mac runs 0.2.x and `status` lists no lanes, run `mv ~/.local/state/agent-env ~/.local/state/agentlane && mv ~/.local/state/agentlane/claims ~/.local/state/agentlane/lanes`. 0.3.0 then uses the folder under its own name. Don't run 0.2.x on that Mac afterwards, because it would start a second registry.

### New

- `agentlane prune` lists the pool simulators and emulators that no lane holds, and `agentlane prune --yes` deletes them to free their disk. It works from the registry, so it covers the `agent-env-pool-*` and `agent-env-emu-*` devices 0.2.x made. Each deletion locks the registry and checks again that no lane of either version holds the device, so a lane claimed meanwhile keeps it. A device the registry has no record of is never deleted, even one with a pool name; the listing shows those apart, because a registry in another state folder may hold them. `--json` prints the listing and each result for tools.
- **Browsers for Intel Macs and Linux.** The pinned Chrome for Testing, its headless shell and ffmpeg now cover Intel Macs and Linux on x64 and arm64, so `up --platform web` installs its browser there without `AGENTLANE_PLAYWRIGHT_BROWSERS`. Linux runs the web half of a project; iOS needs a Mac, and Android on Linux isn't supported yet.
- **Chrome's system libraries on Linux.** `doctor` has a `browser libraries` check that names each library Chrome for Testing needs and the machine lacks, such as `libnss3.so`, and gives Playwright's `install-deps chromium` command as the fix. `up` stops with the same message before it opens the browser.
- Capture hygiene on a simulator has a new `keyboard-intro` step. It marks the keyboard's slide-to-type intro as shown (`com.apple.keyboard.preferences` `DidShowContinuousPathIntroduction` = true) and reads it back, so a fresh simulator's first keyboard no longer opens on an intro that covers the app. `doctor` lists the step with the others.
- The `create-verification-skill` skill tells a project to clear its app's own first-run sheets (onboarding, what's-new, permission prompts) before capturing, and to name them in its run skill.

### Fixed

- On Android, the build hook runs with `JAVA_HOME` set to the JDK the build cache key names: `AGENTLANE_JAVA_HOME`, else `JAVA_HOME`, else the JDK 17 agentlane finds. Before, with `JAVA_HOME` unset, Gradle could run a different JDK from the one the cached build was keyed to.
- On Linux, hooks run with `LANG` and `LC_ALL` set to `C.UTF-8`, which glibc always has, instead of `en_US.UTF-8`, which many images don't generate. `up` refused a web app on such a machine, citing CocoaPods. macOS keeps `en_US.UTF-8`.
- On Linux without `lsof` or `ss`, as in the `node:24` image, `up` reads a port's listeners from `/proc`. Before this, it never found a service's listener and timed out on a server that answered.

## 0.2.1

Fixes from running `setup` from scratch on a production app and on the example app, after 0.2.0 reached them. A project that vendors 0.2.0 should move to this one.

- `maestro test` under a claim keeps a passing run's folder, its `takeScreenshot` files included, and links every run into Maestro's own folder. 0.2.0 deleted a passing run's folder, so a flow's screenshots were lost and scripts reading `~/.maestro/tests` found nothing.
- A second `up --platform web` on a claim whose browser is open works. 0.2.0 failed with "Tracing has already been started".
- A web service started through a package manager (`pnpm exec next dev …`) passes `up`'s check that the server on the port is this worktree's, because a listener anywhere below the started process now counts.
- `init` wires Claude Code once wherever the plugin loads from, and removes the copies an earlier `init` wrote; `doctor` warns when both wire it.
- Every command the CLI and the skills tell you to run is `node_modules/.bin/agent-env …`, which works in every agent's shell.
- Simulator hygiene sets the location again, up to 3 times, when a set doesn't read back.
- Claude Code's SessionEnd hook declares a 10 s timeout, so the release isn't cut off by Claude Code's shared 1.5 s budget.
- The skills: `setup` runs every committed flow and test suite before and after its changes and lists each one; `create-verification-skill` pins the device when flows tap by point, writes a precondition per tool, seeds a page per feature the repo's docs list, and treats a wait that never matches in a sign-in flow as a defect.

## 0.2.0

0.2.0 adds web apps beside mobile apps, per-claim resources, the setup skill and wiring for six agents. A project moving from 0.1.x needs to know the items under "Moving from 0.1.x" first.

### Moving from 0.1.x

- **Run `init` again after you upgrade.** The skill stubs' text changed, so `doctor` warns that a project's stubs are stale until `node_modules/.bin/agent-env init --agents <list>` rewrites them. Warnings don't fail `doctor`.
- **Each claim has an evidence folder.** `$AGENT_ENV_EVIDENCE` (`<state dir>/claims/<id>/evidence`) is set in every hook and under `exec`. It survives `release` and goes when the claim's files are pruned, seven days after the claim ends. `node_modules/.bin/agent-env evidence screenshot | video start|stop | trace start|stop | logs | list` writes there, and a failed `run`, or a failed command under `exec` on a browser claim, keeps its own bundle there.
- **`maestro test` under a claim writes into the evidence folder.** In 0.1.x, Maestro wrote each run to its own folder, `~/.maestro/tests/<run>`. The claim's `maestro` now passes `--debug-output`, and each test's output, its `takeScreenshot` files included, lands in `$AGENT_ENV_EVIDENCE/<stamp>-maestro-test-<pid>/.maestro/tests/<run>/<flow>/`. The folder name ends in `-failed` when the test failed, which is also the path Maestro prints on a failure.
  - Each run is also linked into Maestro's own folder (`~/.maestro/tests/<run>`, or `$XDG_STATE_HOME/maestro/tests/<run>`), so a script that reads it keeps working. Maestro's folder holds the runs of every claim on the Mac, so a script that runs under a claim should read `$AGENT_ENV_EVIDENCE` instead.
  - A `--debug-output` or `--test-output-dir` you pass yourself goes to Maestro unchanged.
- **Printed commands are `node_modules/.bin/agent-env …`.** Every fix line the CLI prints, and every command in the skills and stubs, is written that way, run from the project root, because a bare `agent-env` is on the PATH only in Claude Code with the toolkit's plugin. A run skill that says bare `agent-env` works only there; write the full path.
- **The `device` skill is now `drive`.** It drives browsers too. A `device` skill remains and points to `drive`, so a run skill that names `device` still works.
- **`init` and the Claude Code plugin.** Wherever Claude Code loads the plugin (the project's settings, your local or user settings, or the session running `init`, as `--plugin-dir` does), `init` writes none of the plugin's skills, MCP server or hooks for Claude Code, and says where it found the plugin. It removes the copies an earlier `init` wrote, backing each file up first in `<state dir>/init-backups/`. An agent-env server in `.mcp.json` stays for other agents and is turned off for Claude Code with `disabledMcpjsonServers`. A project whose only agent is Claude Code through the plugin gets no toolkit stubs in `.agents/skills/`. `doctor` warns when the plugin and the project's own files both wire Claude Code.
- **The registry format is unchanged.** 0.1.3 and 0.2.0 worktrees share a Mac's registry: 0.2.0 adds tables that 0.1.3 doesn't read and keeps the format version 0.1.3 checks.

### New

- **Web apps.** `web` in `agent-env.json` names the service that serves the web app and the page to open. `node_modules/.bin/agent-env up --platform web` gives the claim its own browser (a profile, a debugging port and a driver session), opens the app, and signs it in through the `signin` hook, which writes Playwright storage state to `$AGENT_ENV_STORAGE_STATE`. The driver is Playwright (`playwright-cli`) by default, or agent-browser. The toolkit installs Playwright 1.64.0 and agent-browser 0.39.0 with their browsers in its own data folder, so a project's `@playwright/test` must be 1.64.x for its tests to find a browser under `exec`. Browser archives are pinned for Apple silicon Macs only; elsewhere, set `AGENT_ENV_PLAYWRIGHT_BROWSERS`. One claim can hold a device and a browser.
- **Service `platforms`.** A service can be limited to the apps that need it, so a web `up` doesn't start Metro.
- **Resources.** `resources` declares data each claim gets its own copy of, such as a database: a `create` command that exports values to every service, hook and `exec`, and a `teardown` that runs when the claim ends, after a crash too.
- **Six agents.** `node_modules/.bin/agent-env init --agents claude,codex,cursor,copilot,gemini,antigravity` (or `--all`) writes each agent's skill stubs, MCP server and hooks from one source. `--check` exits 1 when a file would change.
- **The setup skill.** It takes a project from no toolkit wiring to `doctor` ready on every platform. `up` and `doctor` name it when `agent-env.json` is missing or invalid, or no agent is wired.

### Fixed

- A service started through a package manager, such as `pnpm exec next dev`, is the service's. `pnpm exec` starts its command in a process group of its own, and `up` refused the server as a process the toolkit did not start. A listener below the service's process now counts, and stopping the service stops it too, even when the wrapper passes on no signal.
- `up --platform web` runs again on a claim whose browser is open. The second run failed at sign-in with "Tracing has already been started"; it now ends the running trace and starts a new one.
- A browser driver error during `up` or `exec` is reported with exit code 1 and a fix that works when `doctor` says ready (close the browser with `node_modules/.bin/agent-env exec -- playwright-cli close`, then `up` opens a new one), instead of escaping with a stack trace.
- `up` sets the simulator's location again, up to three times, when it doesn't read back, as happens on a freshly booted simulator under heavy load.
